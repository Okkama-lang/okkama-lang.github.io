01 /

Name a value.

An Okkama program lives in a .ok file. A module gives it a name; main() is the entry point. Here is a complete first program.

hello.ok · complete runnable file
Download .ok
module tutorial/hello v1.0.0;
import "io/stdout" take Stdout;

main() is int {
    let message = "Hello, Okkama";
    Stdout().writeln(message);
    0;
}
Run hello.ok
okkama hello.ok
Expected output
Hello, Okkama
  • import ... take Stdout names the object we need from the standard library.
  • let gives a value a name. The compiler infers string here.
  • Stdout() constructs an object; writeln is one of its actions.
  • main() is int declares the result type. Its final expression, 0, is the exit status.

TRY IT

Change the message, then run the file again. You have already used a value, an object, an action, and an explicit result type.

02 /

Put behavior in an object.

Objects keep state behind behavior. A bottle can answer whether it is open, but a caller does not assign to its fields directly.

From bottle.ok · declaration excerpt
object Bottle {
    has opened is bool = false;
    Bottle();

    is_open() is bool { opened; }
}

has declares a field. Bottle() is a constructor. The action is_open() returns a bool. The state begins as false, and it is not changed in place.

Ask through behavior

bottle.is_open() makes the object responsible for the answer.

Keep the state inside

The caller works with actions, not a public bag of writable fields.

To open it, the complete example uses a successor action. Download it now or continue to see why a new state gets a new value.

03 /

Let roles describe the protocol.

A payment should be authorized before it is captured. Instead of exposing every action at every point, give each stage a role. A role describes the behavior available through a particular view.

Createdstatus()
authorize()
→
Authorizedstatus()
capture()
→
Capturedstatus()
No next transition

Three views. Only the actions that belong at each step.

From payment.ok · role declarations
role Created {
    status() is string;
    authorize() is ^Authorized;
}

role Authorized {
    status() is string;
    capture() is ^Captured;
}

role Captured {
    status() is string;
}

Notice what is missing: Created has no capture(). The result of authorize() is a successor viewed as Authorized, where capture becomes available.

A role is a contract, not an inheritance hierarchy. The payment implementation can satisfy all three roles while a caller sees only the role it was given.

READ THE SIGNATURE

authorize() is ^Authorized says: this transition returns a successor through the Authorized contract. The caret ^ makes that promise explicit.

For more detail, read Roles in the language book.

04 /

New state. New value.

Now implement those contracts. The Payment object has an internal stage. The implementation is hidden; callers obtain it through a public object that returns the Created role.

From payment.ok · hidden implementation
hidden enum Stage = (created, authorized, captured);
enum PaymentError is Error = (invalid_transition);

hidden object Payment does Created, Authorized, Captured {
    has stage is Stage = Stage.created;
    Payment();

    status() is string {
        match stage {
            case Stage.created { "created"; }
            case Stage.authorized { "authorized"; }
            case Stage.captured { "captured"; }
        }
    }

    authorize() is ^Payment {
        confirm stage == Stage.created else throw PaymentError.invalid_transition;
        ^stage = Stage.authorized;
    }

    capture() is ^Payment {
        confirm stage == Stage.authorized else throw PaymentError.invalid_transition;
        ^stage = Stage.captured;
    }
}

^stage = Stage.authorized; describes the state of the successor. It does not assign a new state to the original payment.

The confirm guards protect the implementation's state rules. A failed guard throws a case of PaymentError, an enum that implements Error. The role view and the internal check serve different purposes.

From payment.ok · public construction boundary
object Payments {
    Payments();
    create() is Created { Payment(); }
}

Payments().create() returns Created, not the concrete implementation. That boundary is what keeps the next available action narrow.

Immutable does not mean “nothing happens.”Actions can communicate with the outside world. Here, immutability means the values themselves are not rewritten. Side effects still need explicit design.

Read more in Successor actions and immutability.

05 /

Read the story in the code.

Put the parts together in one file. Each transition has a named result, so the valid sequence reads like the domain.

From payment.ok · entry point
main() is int {
    let out = Stdout();
    let created = Payments().create();
    let authorized = created.authorize();
    let captured = authorized.capture();
    out.writeln("Original: " + created.status());
    out.writeln("After authorization: " + authorized.status());
    out.writeln("After capture: " + captured.status());
    0;
}
Download complete payment.ok
Check, then run
okkama check payment.ok
okkama payment.ok
Expected output from the run
Original: created
After authorization: authorized
After capture: captured

The successful check command is silent. The run prints three different states: creating a successor leaves the original value intact.

THREE NAMES, THREE VALUES

created, authorized, and captured remain available. None is a mutable variable that silently changes meaning.

06 /

Learn where the guarantees stop.

Capture too early

In the entry point, use created.capture() instead of authorized.capture(). The prepared invalid file makes exactly this change.

Check the invalid transition
okkama check payment-invalid.ok
Expected compiler diagnostic · exit status 1
payment-invalid.ok:54:28: semantic error: Role "Created" has no action "capture"

Discard the next state

Calling a successor action without using its result is also rejected. The prepared file replaces the capture binding with authorized.capture(); and removes the later print that used captured.

Check the discarded successor
okkama check payment-discarded.ok
Expected compiler diagnostic · exit status 1
payment-discarded.ok:54:5: semantic error: Successor action result must be used

What this does not guaranteeThis is a local model, not a payment processor. It does not consume the original value or make external effects happen exactly once. Two workers can still race against a database or call a provider twice. Real systems need transactions, idempotency, concurrency control, and explicit failure handling.
